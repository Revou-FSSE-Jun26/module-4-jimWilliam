# Guideline violation report

Violations found while reviewing AI-generated RevoTask code against `/guidelines`, each with the rule it breaks, how it was found, and the fix that was applied. Every fix is in the commit history and covered by a test where one applies.

| # | Where | Guideline | What was wrong | How it was found | Fix applied |
|---|---|---|---|---|---|
| 1 | `backend/tests/` (first generated suite) | BE-11 Every route has tests for success and each documented error | The suite covered the main paths but skipped documented errors for many routes: no 401 check on most routes, no 403 for non-members on B14–B20, no 404 for unknown ids on B10–B22, no test of the 500 handler. | Reading the route table in `design.md` against the test files. | Added `tests/test_access_matrix.py`: 401 over every protected route, a non-member 403 matrix that also asserts nothing changed, a member-vs-admin 403 matrix, parametrised 404s, and a 500 test that asserts no stack trace. 51 → 71 tests. |
| 2 | `frontend/components/board/CardItem.tsx` | FE-09 Every control is reachable and labelled ("never remove the focus ring without a 3:1 replacement") | The card title button had `focus-visible:outline-none`, so keyboard users saw no focus on cards. The same button was stretched over the whole card with an `::after` overlay, and Chrome does not start a native drag from a `<button>`, so mouse users could not drag cards either (R15.1). | The Playwright journey's drag step never fired `drop`; a drag-event trace showed why. The focus override was found in the same review. | Removed the outline override and the overlay. The card itself opens the detail on click (ignoring clicks on controls), and the title stays a real button with the default focus ring and `draggable={false}`. The Kanban journey now drags and persists. |
| 3 | `BaseButton`, `BaseModal`, `TopBar`, `NavDrawer`, `Avatar`, `Sidebar` | FE-07 Style with design tokens ("use token utilities instead of raw hex, px radii or ms values") | Hover tints were hard-coded as `bg-[rgb(159_216_203/0.12)]` (wrong in the light theme), the avatar used `text-[#0E2A33]`, and the brand mark used an arbitrary `rounded-[…]` radius. | `grep` for arbitrary values in `components/` during review. | Added `--hover-tint` (one value per theme) as the `bg-hover` utility, `--color-avatar-ink`, and a `.brand-mark` class. `grep` now finds 0 raw colors or radii in components. |
| 4 | `frontend/components/shared/BaseModal.tsx` and its callers | FE-09 Every control is reachable and labelled | Modal forms used React's `autoFocus`, which runs when the component mounts, before `showModal()` opens the dialog. The browser then focused the close button, so a keyboard user who opened "New board" and typed lost their input. | Manual check in Chrome: the typed board name went nowhere. | `BaseModal` focuses the element marked `data-autofocus` (or the first field) right after `showModal()`; modal fields use `data-autofocus`. Covered by `__tests__/shared.test.tsx` ("focuses the marked field when it opens"). |
| 5 | `frontend/components/dashboard/BoardGrid.tsx` | FE-06 Buttons are BaseButton | The dashboard's "New board" tile was a one-off `<button>` with its own hover and focus styles. | Button audit for task 16.11 (`grep '<button' app/`). | The tile is now a `BaseButton` (ghost variant) with layout classes; no page renders a raw `<button>`. |
| 6 | `frontend/components/layout/ProfileMenu.tsx` | FE-09 Every control is reachable and labelled | The profile capsule had `aria-label="Account menu for <name>"`, which replaced its visible text in the accessible name (WCAG 2.5.3 Label in Name), so a voice-control user saying the visible name would not match. | The axe scan in `e2e/visual.spec.ts` (`label-content-name-mismatch`, serious). | Replaced the `aria-label` with a visually hidden "Account menu:" prefix, so the visible name stays in the accessible name. The axe scan reports 0 serious or critical issues on every page in both themes. |
