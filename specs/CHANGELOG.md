# Spec CHANGELOG

This file records each refinement round of the RevoTask specs. Every entry shows what the AI-generated text said before, what it says after, why it changed, and the refinement prompt that targets the gap, so that the round can be replayed in Kiro.

- **v1**: `requirements.md`, `design.md` and `tasks.md` generated by Kiro (fast-task workflow) from the project brief. A copy is kept in `specs-history/v1/`.
- **v2**: review of v1 against the RevoTask brief and the grading rubric (AI-assisted review, checked by hand). Entries 1–10 below.
- **v2.1**: UI/UX design system added on stakeholder request, checked against the modern-web-guidance guides. Entries 11–13 below.
- **v3**: findings that came up while implementing the backend, frontend and tests. Entries 14 onwards.

Review method used for v2: every line of the brief's Requirements, Deliverables and Grading Rubric was checked against the spec. Each gap was classed as **Blocker** (a rubric item would fail), **Major** (a brief feature is missing or wrong), or **Minor** (wording or traceability).

## v2 — Review against the brief and rubric

### 1. Session lost on page reload (Blocker)

- **Before (R21.8, design "Risks"):** "THE AuthContext SHALL keep the JWT in memory-backed React state." The design accepted that "a page reload clears it, so the user returns to /login", and said the Server Components would get the token "through a thin client wrapper".
- **After (R12.4, R12.6, R13.1, R14.1, R21.8, new R32):** the JWT is stored in an `HttpOnly`, `Secure`, `SameSite=Lax` Session_Cookie set by a Server Action. The root layout reads it to initialise AuthContext, the Server Components read it to call the API, and `middleware.ts` guards protected routes.
- **Why:** the rubric checks that "the card stays in the new column after a page refresh", and the Playwright journey reloads the page. With the token only in memory, every reload logged the user out, so both checks failed. The brief also requires the Dashboard and Board Detail to be Server Components, and a Server Component cannot read client React state, so they could not have fetched anything.
- **Refinement prompt:** "The JWT is kept only in React state, so a reload logs the user out and the Server Components for / and /boards/[id] cannot authenticate. Store the JWT in an HttpOnly Secure SameSite=Lax cookie set by a Next.js Server Action, read it in the root layout and in the Server Components with cookies(), and add a middleware.ts route guard. Update requirements, design and tasks, and keep localStorage forbidden."

### 2. Folder paths do not match the rubric (Blocker)

- **Before (design layout):** `backend/app/auth/ boards/ …` and `frontend/src/components/ BaseButton BaseBadge BaseModal …`.
- **After (R11.1, R11.2, R20.5, design layout, task 4.1, task 15.1):** `backend/app/blueprints/<name>/{routes,service,schema}.py` and `frontend/components/shared/{BaseButton,BaseBadge,BaseModal}.tsx`, with `hooks/` and `lib/` at the frontend root.
- **Why:** the rubric checks for literal paths: "app/blueprints/ has folders for auth, boards, …" and "components/shared has BaseButton, BaseBadge, and BaseModal". Code generated from v1 would have put files in the wrong places.
- **Refinement prompt:** "The brief and rubric require app/blueprints/<name>/ for the eight Flask blueprints and components/shared/ for BaseButton, BaseBadge and BaseModal. Update the design layouts, the glossary and the scaffold tasks to use exactly these paths."

### 3. The two user roles were missing (Major)

- **Before (glossary, R2):** "Board: A named container owned by a User." Access was a single `owner_id` check, and no requirement mentioned administrators or members.
- **After (intro, glossary, R2.1–R2.8, R8.1, R8.4, R14.5, new R31, `board_members` table, routes B27–B29, `require_member` helper, Property 7, Property 35):** each board has members with the role `member` or `admin`. Admins manage member access, rename or delete the board, and see analytics. Members work on columns, cards and comments.
- **Why:** the brief names two user types, "Board members" and "Board administrators who manage member access". With owner-only access, "member activity" analytics and card assignment had nobody to refer to except the owner, and the rubric needs the user roles written in the project brief.
- **Refinement prompt:** "The brief defines board members and board administrators, but the spec has only a board owner. Add a board_members table with role admin|member, make the creator an admin, add GET/POST/DELETE /api/boards/<id>/members in the boards blueprint, restrict rename/delete/analytics/member management to admins, and never allow a board with zero admins. Add the acceptance criteria, routes, traceability rows and tasks."

### 4. Logout missing, E2E scenarios not named (Blocker)

- **Before (R26.2, R26.3):** "THE Playwright_Suite SHALL contain 4 auth scenarios." / "…a Kanban journey of 8 steps…". No requirement covered logging out.
- **After (R26.2, R26.3, R26.6, R32.5, R32.7, design Testing Strategy, tasks 20.1–20.3):** the 4 scenarios are named (login redirect, invalid credentials, unauthenticated redirect, post-logout redirect), the 8 steps are listed, a Log out button is required, and each run registers a unique user.
- **Why:** the brief's E2E deliverable needs a "post-logout redirect" scenario, which cannot pass without a logout feature. Unnamed scenarios also leave Kiro to invent its own, which may not match the rubric.
- **Refinement prompt:** "List the 4 Playwright auth scenarios and the 8 Kanban journey steps exactly, add a Log out requirement that deletes the session cookie and redirects to /login, and make each E2E run create a unique user so it can run repeatedly against production."

### 5. Card search leaked other users' cards (Major, security)

- **Before (R5.2, design "Search"):** "THE Backend SHALL return the Cards whose title or description contains the term". The query filtered only on text and `deleted_at`.
- **After (R5.2, design "Search and My Tasks", Property 17, task 8.2):** search joins `Card → Column → Board → BoardMember` and returns only cards on boards where the user is a member.
- **Why:** any signed-in user could search for "salary" and read cards from every board in the database. This broke the NFR "users can only see data on boards they belong to".
- **Refinement prompt:** "GET /api/cards?search= is not scoped to the requesting user. Restrict it, and ?assignee=me, to cards on boards where the user is a board member, and extend Property 17 so it generates cards on boards the user cannot access."

### 6. Field names did not match the brief (Minor)

- **Before:** Boards and Columns had a `title`; `ApiError` had a `status` field.
- **After (glossary, R2.1, R2.4, R3.1, R3.2, R13.2, R21.5, design data models and `lib/errors.ts`):** Boards and Columns have a `name`; `ApiError` has `statusCode` and `message` and lives in `lib/errors.ts`.
- **Why:** the brief says "update board name", "update column name" and "a typed ApiError class with statusCode and message fields".
- **Refinement prompt:** "Rename Board.title and Column.title to name, and ApiError.status to statusCode, to match the brief. Put ApiError in lib/errors.ts and import it in lib/apiClient.ts."

### 7. Drag and drop did not work on mobile (Major)

- **Before (R15, R27.5):** native HTML5 drag and drop only, and "THE Frontend SHALL render every page without horizontal scrolling".
- **After (new R33, R27.5, design `moveCard` and MoveControl, Property 36, task 16.5):** every card has a keyboard-accessible "Move to" select that calls the same `moveCard` function as the drop handler. The Kanban row may scroll inside its own container.
- **Why:** HTML5 drag events do not fire on touch screens, so on a phone cards could not be moved, and the rubric checks that the live app is usable at mobile size. The "no horizontal scrolling" rule also contradicted a multi-column Kanban at 375 px.
- **Refinement prompt:** "Native HTML5 drag and drop does not work on touch devices. Add a keyboard-accessible Move to select on each card that reuses the same move function as useDragAndDrop (optimistic update, PATCH position, revert on error), and allow the Kanban columns to scroll horizontally inside their own container on mobile."

### 8. My Tasks was not grouped by board (Minor)

- **Before (R17):** "THE Frontend SHALL provide the /my-tasks page that lists Cards from GET /api/cards?assignee=me."
- **After (R5.1, R17.5, R17.6, B13 response shape, task 16.8):** B13 returns `board_id` and `board_name`, and /my-tasks groups cards under their board name and links each card to its board.
- **Why:** the brief says the list is "grouped by board name".
- **Refinement prompt:** "The brief says My Tasks is grouped by board name. Return board_id and board_name from GET /api/cards and group the /my-tasks list by board."

### 9. Project brief and guideline comparison under-specified (Blocker)

- **Before (R22.1, R23.4):** the Spec_Set had no brief, and R23.4 asked only for "one comparison of AI output before and after the guidelines were applied".
- **After (R22.1, R23.4, new `brief.md`, task 1.1):** `brief.md` holds the overview, roles, core features, tech stack and 5 NFRs. The comparison must count guideline violations in both outputs of the same prompt.
- **Why:** the rubric requires "a project brief … with overview, user roles, core features, tech stack, and at least 2 non-functional requirements", and the brief requires a comparison "showing measurable improvement".
- **Refinement prompt:** "Add a brief.md to the spec set with overview, user roles, core features, tech stack and at least 2 NFRs. Change the guideline comparison requirement so it counts violations in the AI output before and after the guidelines for the same prompt."

### 10. Smaller precision fixes (Minor)

- **Before → After:**
  - R1.4 "return … a JWT" → returns the JWT, its expiry and the user; new R1.8 sets the expiry from `JWT_ACCESS_TOKEN_EXPIRES_HOURS` (the brief says "JWT token with expiry").
  - R12 had no client-side validation → new R12.7 (controlled inputs, email format, 8-character password), as the brief requires.
  - R20.2 "BaseBadge SHALL render a short text label" → color variants listed (the brief says "with color variants"); new R20.6 forbids raw `<button>` on pages (rubric: "pages such as My Tasks and Profile use BaseButton").

  - Moving a card to a column on another board was a design "assumption" → R31.10 returns 400.

## v2.1 — UI/UX design system

Stakeholder request: a glassmorphism interface with curved glass, a strong background, smooth transitions and hover animation, nested navigation, an interactive profile section and a curved sidebar, responsive from mobile to 4K, following modern web guidance. The guidance came from the `modern-web-guidance` guides `motion`, `natural-interactions`, `menu`, `navbar`, `navigation-drawer`, `dialog`, `animate-element-entry-exit`, `animate-to-from-top-layer`, `same-document-transitions` and `responsive-design`.

### 11. Visual design was unspecified (Major)

- **Before (R20, design "Shared components"):** the only visual requirements were the BaseButton variants, "BaseBadge with color variants" and "Tailwind responsive classes".
- **After (new R34–R39, design "UI/UX Design System", tasks 15.12–15.18, 16.19–16.25, 18.5, 20.5, Properties 37–40):** a token system (color for two themes, three glass levels, radius by hierarchy, tinted elevation, motion), Fraunces and Figtree typography, the App_Background, the curved Sidebar with Nav_Tree, Nav_Drawer and Top_Bar, the Profile_Capsule and Profile_Menu, Appearance_Preferences, a motion table with reduced-motion behaviour, breakpoints up to 3840 px, and a fallback table for every newer platform feature.
- **Why:** without a written design, each generated component would invent its own colours, radii and animations, and nothing would be testable. Every new criterion is measurable (contrast ratios, widths, durations, attributes).
- **Refinement prompt:** "Add a UI/UX design system to the spec: a sea-glass glassmorphism look with three surface levels, a curved floating sidebar with nested navigation, an interactive profile menu with appearance settings, motion for entries, hover, modals and card moves, and layouts from 320 px to 3840 px. Write it as EARS acceptance criteria, a design section with tokens and wireframes, and tasks, and use native dialog, popover and view transitions with feature-detected fallbacks."

### 12. BaseModal re-implemented what `<dialog>` already does (Minor, accessibility)

- **Before (R20.3, design "Shared components", task 15.5):** "BaseModal (titled overlay, close control, closes on Escape, `role=\"dialog\"` with `aria-modal`)".
- **After (R20.3, design, task 15.5):** BaseModal is a native `<dialog>` opened with `showModal()`, named with `aria-labelledby`, with `closedby="any"` and no `role="dialog"`, `aria-modal`, focus trap or Escape handler.
- **Why:** the `dialog` guide says a native modal already provides the inert page, focus containment, the top layer, Escape and focus return, and that adding `role="dialog"` or `aria-modal` to it is wrong. A hand-built overlay also needs its own focus trap, which v1 never specified.
- **Refinement prompt:** "Change BaseModal to a native dialog opened with showModal(), named by aria-labelledby, with closedby=\"any\". Remove role=\"dialog\", aria-modal, any focus trap and any Escape handler, and add overscroll-behavior: contain to dialog:modal and ::backdrop."

### 13. Log out moved into the Profile_Menu (Minor)

- **Before (R32.7, task 15.6):** "THE shared header SHALL contain a Log out control rendered with BaseButton."
- **After (R32.7, tasks 15.17 and 20.2):** "THE Profile_Menu SHALL contain a Log out command." The Playwright scenario (d) logs out through the Profile_Capsule.
- **Why:** with a Sidebar and Profile_Capsule there is no separate header for account actions; account actions belong together in the profile menu. Keeping the E2E step in sync stops the post-logout scenario from failing.
- **Refinement prompt:** "Move Log out into the profile menu and update the post-logout Playwright scenario to open the profile capsule first."

## v3 — Findings during implementation

### 14. Column delete could not soft-delete its Cards (Major, contradiction)

- **Before (R3.3, task 7.4):** "THE Backend SHALL delete the Column, soft-delete its Cards and return status 200."
- **After (R3.3, task 7.4):** "THE Backend SHALL delete the Column together with its Cards and their Comments and return status 200."
- **Why:** `cards.column_id` is `NOT NULL` with a foreign key to `columns`. Once the Column row is gone, a soft-deleted Card would point at nothing, and the cascade removes the Card rows anyway. Soft delete (DB-03) stays for Cards deleted on their own, which is what R4.4 asks for.
- **Refinement prompt:** "R3.3 asks to soft-delete the cards of a deleted column, but cards.column_id is NOT NULL with ON DELETE CASCADE. Resolve the contradiction: either soft-delete columns too or delete the column's cards with it, and update the requirement and task."

### 15. Analytics promised data the model does not record (Minor)

- **Before (design "Notable response shapes"):** `"activity_per_member": [{..., "comments": 4, "cards_updated": 7}]`
- **After (design and `analytics/service.py`):** `"cards_assigned"`, the number of live Cards assigned to the member, plus `week_start` so the frontend can label the week.
- **Why:** no table records who updated a Card, so `cards_updated` could not be computed without adding an audit log, which is out of scope.
- **Refinement prompt:** "activity_per_member.cards_updated needs an updated_by field that the model does not have. Replace it with a metric the schema supports and document the change."

### 16. The spec targeted an older Next.js (Major)

- **Before (design layout, R12.6 glossary, task 15.3):** a `middleware.ts` route guard, and nothing about Next.js caching.
- **After:** the guard is `proxy.ts` (Next.js 16 renamed `middleware.ts`), and `next.config.ts` turns off `cacheComponents` and `partialPrefetching`, which `create-next-app` 16.4 enables by default.
- **Why:** checked against the current docs (Context7 and the docs bundled in `node_modules/next/dist/docs`). With Cache Components on, reading `cookies()` outside a `<Suspense>` boundary is a build error, yet the root layout must read the session and appearance cookies so a reload stays signed in (R32.2) and the first paint has the right theme (R36.6). Every RevoTask page is per-user data, so there is nothing to cache.
- **Refinement prompt:** "Check the design against Next.js 16.4: replace middleware.ts with proxy.ts, and decide whether Cache Components fits pages that read the session cookie in the root layout."

### 17. View Transitions through React instead of a custom helper (Minor)

- **Before (design "Motion specification", task 15.18):** a `lib/viewTransition.ts` helper calling `document.startViewTransition(() => flushSync(update))`.
- **After:** React 19.3's `<ViewTransition>` with `name` and `share`. Next.js navigations are already transitions, so the nav pill glides with no extra code, and card moves update state inside `startTransition`.
- **Why:** the Next.js 16 view-transitions guide documents this as the supported integration. `flushSync` inside `startViewTransition` fights React's own scheduling, and the declarative version is less code with the same fallback (no animation where unsupported).
- **Refinement prompt:** "Use React's <ViewTransition> for the nav pill glide and card moves instead of a hand-written startViewTransition helper."

### 18. Token contrast failed its own test (Major, accessibility)

- **Before (design token tables):** dark muted text `#B9D3CC`, dark error text `#FF9AA8`, pane fill alpha `.55`, pebble tint `.16`, light sea glass `#2E7D74`.
- **After:** muted `#C7DED8`, error text `#FFC2CA`, pane alpha `.60`, pebble tint `.12`, light sea glass `#236B63`.
- **Why:** the Property 37 test (`__tests__/tokens.test.ts`) composites each fill over the brightest point of the background. Muted text on a pebble measured 4.00:1 and error text on a pebble 3.15:1, both below the 4.5:1 that R34.6 requires. All 30 checked pairs now pass in both themes.
- **Refinement prompt:** "Run the token contrast test against the worst-case background and adjust the failing text colors and glass alphas until every pair meets 4.5:1 (text) and 3:1 (UI)."

### 19. Property 29 promised more than FLOAT order can deliver (Minor)

- **Before (Property 29):** "For any two neighbour order values `prev < next` … `computeOrder` returns a value strictly between them."
- **After:** the property holds whenever a double-precision value exists between the neighbours; when none exists, precision is exhausted, which is the limitation already accepted under "Float precision" in Data Models.
- **Why:** fast-check found the counterexample `prev = 999999999.9999987`, `next = 999999999.9999988`: adjacent doubles, so the midpoint equals one of them. R30.5 (a move updates one row) rules out rebalancing during a move, so the property was corrected rather than the code.
- **Refinement prompt:** "fast-check shows computeOrder cannot stay strictly between adjacent doubles. Restate Property 29 with that precondition and link it to the documented float-precision limitation; keep rebalancing as a follow-up."

### 20. Deployment moved to Vercel and Supabase (project owner's decision)

- **Before (R27.1–R27.3, brief, design, task 19.1):** "THE Backend SHALL be deployed on Railway and run with Gunicorn", with `railway.json` running `flask db upgrade` as a pre-deploy command.
- **After:** the Flask API is a Vercel Python function (`wsgi.py` exports `app`; `backend/vercel.json` trims the bundle) and the database is Supabase PostgreSQL. A new R27.6 requires the transaction pooler (port 6543) with prepared statements off and no client-side pool; migrations run with `flask db upgrade` over port 5432 before a deploy. `railway.json` and `Procfile` were removed.
- **Why:** the project owner chose Vercel and Supabase only. Supabase's transaction pooler does not support prepared statements (checked in the Supabase docs via Context7), and serverless functions should not hold their own connection pools, so the engine settings depend on the port.
- **Refinement prompt:** "We deploy on Vercel and Supabase only. Replace the Railway deployment requirements and config with a Vercel Python function for the Flask API and a Supabase Postgres database, including pooler settings and how migrations are applied."

## v4 — Project owner's feature round

### 21. Rich-text descriptions, profile photos and card images (project owner's request)

- **Before (R16, R18, R36.7, Nav_Tree):** descriptions were a plain `<textarea>`; Avatars were initials only; the main navigation had a "Profile" link as well as the Profile_Capsule, so the profile appeared twice.
- **After:** new Requirements 40–43, routes B30–B35 (B32–B35 in a ninth `media` Blueprint), Properties 41–45 and task group 23. Descriptions use a TipTap toolbar editor and are sanitised server-side with nh3. Avatars and card images are converted to AVIF in memory with Pillow (the original is never stored) and kept in Supabase PostgreSQL. Images are served through short-lived HMAC-signed URLs and shown through a ProtectedImage component (no context menu, drag-out or long-press save) and a lightbox. The duplicate Profile link was removed.
- **Why:** the project owner asked for a profile photo stored as AVIF with the original deleted, a clickable but download-protected picture, image attachments on cards and a full formatting toolbar. Vercel's filesystem is read-only, so images go in the database. `<img>` tags cannot send the JWT and the API is on another domain, so Signed_URLs carry their own credential. User HTML is only safe to render after server-side sanitising, so the API (not the editor) is the trust boundary. Library APIs were checked in Context7 (Pillow 13 AVIF options, TipTap 3 StarterKit with Underline and Link). Blocking right-click is only a deterrent, and the requirement says so rather than promising DRM.
- **Refinement prompt:** "The profile tab is doubled; keep the one at the bottom. Let users change their profile picture, convert it to AVIF and delete the original. The picture can be clicked but is protected from download (no right-click). Allow image attachments on cards, and give the description a full rich-text toolbar (bold, italic, underline, etc.)."

### 22. Full-height sidebar with one scroller (project owner's request)

- **Before (R35.1, R35.5, design "Curved Sidebar"):** the Sidebar floated 0.75rem from the viewport edges, and the Boards list had its own `max-height: 40dvh` scroller inside the scrolling nav. With a few boards and one expanded, the list was cut off half-way through the current page's pill while empty space was left below My tasks.
- **After:** the Sidebar runs the full viewport height, flush with the start edge, with a lit curved rim and a tide decoration behind the Profile_Capsule. The nav is the only scroller; its scrollbar is hidden and its edges fade with a scroll-driven animation (a thin scrollbar remains where that is unsupported). Dashboard and My tasks come before Boards; boards have colour dots, open card counts and guide lines. New R35.11; R35.5 no longer lists Profile (removed in entry 21).
- **Why:** the project owner saw a scrollbar in the sidebar and asked for a more interesting, full-height design. Two nested scrollers made the cut-off likely, and a floating pane wasted height on small laptops. The visual suite's settle helper waited for every running animation to finish; scroll-driven animations never finish, so it now skips them.
- **Refinement prompt:** "There was a scroll in the sidebar. Change the design to be more interesting and full height."

### 23. Full-height board, quiet scrolling and the Tide_Clock (project owner's request)

- **Before (R38.4, design "Kanban"):** Columns were capped at `100dvh - 9rem` and sized to their content, the Kanban row showed a horizontal scrollbar, a mouse wheel could not move it sideways, and the document showed its own scrollbar. There was no clock.
- **After:** new Requirements 44 and 45, Properties 46 and 47, task group 25. The board page is one viewport tall; columns run to the bottom and only their card lists scroll. The row scrolls sideways with no scrollbar, edge shades and arrows where there is more, the wheel turned sideways, and a dock of column chips that shows what is in view and jumps to a column. Document, nav and card-list scrollbars are hidden where scroll-driven animations can show progress instead (a lifting Top_Bar and a bottom shade). The Tide_Clock sits above the Profile_Capsule: time (click for 12/24-hour), date, the tide of the day, and a link to the cards assigned to you; the sidebar's waves rise and fall with the same tide.
- **Why:** the project owner asked for the main page to scroll like the sidebar (down and sideways), to be full width and full height, and for a clock placed where it reads best. The clock goes above the profile rather than bottom right, because the bottom right of the board is where the last column and the dock live, and because tying it to the existing tide decoration makes it part of the design instead of a widget on top. The row is not masked for its fades: a mask would make it a backdrop root and break the columns' glass blur.
- **Refinement prompt:** "Make the main page scroll down and left/right like the sidebar, full width and full height, and more interesting. Add a clock, in the bottom right or above the profile at the bottom left, with a brilliant idea."

### 24. Full-bleed board row, board progress and a simpler Nav_Tree (project owner's request)

- **Before (R35.5, R44, design "Board_Stage"):** after scrolling the Kanban sideways, the row's left edge and its edge shade showed as a box next to the Sidebar. Each board in the Nav_Tree opened a sub-list with Board, Members and Analytics links that repeated the board's own Top_Bar buttons. Boards showed only a card count.
- **After:** the row is full-bleed, so Columns slide under the frosted Sidebar and blur out; the edge shades are gone. Board rows are direct links with a progress liquid (Cards in the last Column out of all Cards, the Analytics rule), `done/total` or a check at 100%, and live updates from the open board. New R44.6 and R46, Properties 48 and 49, task group 26; GET /api/boards gains `done_count`. The Tide_Clock's assigned count now refreshes after each navigation.
- **Why:** the project owner saw the box at the left edge and asked to hide it with blur, proposed a liquid progress bar per board, and asked whether the sidebar's Members and Analytics links doubled the Top_Bar. They did: the same panels, reached two ways, at the cost of an extra level in every board row. "Done" is the last Column rather than a Column named "Done", because names are free text and Analytics already uses the last Column. The owner also asked whether to move the "cards assigned to you" chip; it stays under the clock (reasons in the reply), with fresher data.
- **Refinement prompt:** "When I scroll right there is a box-like line on the left; hide it with the blur so it looks full width. Give each board in the sidebar a liquid progress bar, 100% when every task is done. Do the Members and Analytics links in the sidebar double the top bar? Should the assigned-cards chip move?"

### 25. Board purpose, colour, column management, board notes, links and photos, and the brand mark (project owner's request)

- **Before (R2, R7, design "Board settings"):** Board settings only renamed or deleted the board. Columns were added only at the end of the Kanban and could not be reordered from one place. Boards had no stated goal, nowhere to keep meeting notes or recordings, and a colour derived from the id. The brand mark was a plain sea-glass blob and the favicon was the framework default.
- **After:** new Requirements 47–50, routes B36–B41 (B3, B4, B5, B6 and B34 extended), Properties 50–52, task group 27. Board settings has general and appearance (name, purpose, colour), a column manager (add "Ideas" before "To do", rename, reorder, delete with a card count) and a danger zone. Every member sees the purpose under the title and in "About this board", with shared rich-text notes, pinned links and AVIF photos. The logo is the favicon, the app icons and the in-page brand mark.
- **Why:** the project owner asked for appearance settings, managing columns from settings, a board purpose "so members remember their main target", and attachments such as meeting notes, recordings and photos. Notes are rich text rather than uploaded files, so they are searchable, editable by the team and safe to render after sanitising. Recordings and documents are links, not uploads: the Vercel request limit and database storage suit small images, not video or PDFs. The colour is a hue from a fixed palette at one lightness and chroma, so no choice can break contrast.
- **Refinement prompt:** "In board settings, set up the appearance (the dot colour) and the columns (for example add Ideas before To do). Show the board's purpose so members remember the main target, set when creating a board or in settings, with attachments such as meeting notes, recordings or photos. Use the README logo for the favicon and the in-page brand mark."

### 26. Due dates, a cleaner board, one-scroll dialogs, custom colours, a collapsible sidebar and smoother entrances (project owner's request)

- **Before (R37.3, R48, R49, BaseModal):** the Kanban ended with a full "Add a column" form; columns in settings moved only with arrow buttons; colours were eight presets; cards and boards had no dates; Board settings showed two scrollbars (the dialog's own `overflow: auto` and the body); only the card dialog became a sheet on phones; the sidebar could not be collapsed on wide screens; entrances took 240 ms with a 40 ms stagger.
- **After:** new Requirements 51–53, R37.3, R48.4, R49.6 and R49.7 changed or added, Properties 53–56, task group 28. ### 28. The API moves to Render with Gunicorn (project owner's decision)

- **Before (R27, entry 20):** the Flask API ran on Vercel as a Python function, connected through Supabase's transaction pooler (port 6543) with no client-side pool, and `backend/vercel.json` trimmed the bundle. The 4 MB upload limit was justified by Vercel's 4.5 MB request limit.
- **After:** the API runs on Render as a web service served by **Gunicorn** (`gunicorn wsgi:app --config gunicorn.conf.py`: threaded workers on `$PORT`, 60 s timeout), defined in a root `render.yaml` Blueprint with the health check `/api/health`. The build command runs `flask --app wsgi db upgrade` (pre-deploy commands need a paid plan). The API now uses Supabase's session pooler (port 5432, IPv4) with a small pool per worker (3 + 2, checked, recycled every 5 minutes); the transaction-pooler path stays for serverless hosts. The frontend stays on Vercel and the database on Supabase. `backend/vercel.json` was removed. Images still live in PostgreSQL, now because Render's filesystem is ephemeral; the 4 MB limit stays to keep the database small.
- **Why:** the project owner chose Render for the backend and Vercel for the frontend, which also brings back Gunicorn, the server the course brief lists. A long-running server can keep a connection pool, which removes a connection handshake from every request. Render's own Postgres free plan expires after 30 days, so the database stays on Supabase. Render's free instances sleep after 15 minutes without traffic and take about a minute to wake, which the README and the latency check now mention.
- **Also fixed:** while re-running the suite, Hypothesis found that Property 13 failed for `"order": "1"`: marshmallow's `Float` accepts numeric strings (and the column reorder schema also accepted NaN). A `JsonNumber` field (`app/common/fields.py`) now accepts only real JSON numbers for both, with a regression test.
- **Refinement prompt:** "I changed my mind: I will use Render for the backend and Vercel for the frontend, so we can still use Gunicorn."

### 29. Faster page loads: co-located regions and per-request deduplication (project owner's request)

- **Before:** Vercel ran the Next.js server functions in `iad1` (Washington, USA) by default while the API runs on Render in Singapore, so every server-side API call (session, sidebar boards, page data) crossed the Pacific twice. The dashboard also fetched `/api/boards` twice per load (layout and page).
- **After:** `frontend/vercel.json` pins the functions to `sin1` (Singapore). `serverFetch` and `getSessionUser` go through React's `cache()`, so identical API calls within one server request are made once. No API-side response cache was added.
- **Why:** the owner asked for an API cache for faster loading. Measuring first showed the delay was distance, not the API: `/api/health` answered in about 0.1 s, while `x-vercel-id` showed the functions in `iad1`. A shared response cache in Flask would add stale-data and permission risks (two Gunicorn workers, per-user data) for a few milliseconds of database time; the per-request cache has neither risk. Remaining factors: the free Render instance sleeping after 15 idle minutes, and the Supabase project's region (best in Singapore, `ap-southeast-1`).
- **Refinement prompt:** "Can you add an API cache for faster loading?"
